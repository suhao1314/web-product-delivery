# 网页审美方向与改版护栏

用于新建官网、活动页、产品页和网页后台，也用于用户说“页面丑”“想整体换风格”的改版。目标是把审美判断落成可看、可点、可回退的页面选择。

## 先审图再开发

从一条代表性任务定稿。图中画出用户需要认出的入口、主动作和真实结果，并补上这条路上会发生的失败或返回状态。[按任务排版和补齐状态](ui-design-practice.md#按任务排版和补齐状态)

1. 新建页面或重做主要版式时，交真实可看的 UI 示意图。以访客使用的桌面和移动尺寸画出首屏、完整阅读顺序、真实文案或有标注的示例，再附代表性按钮与交互状态。展示已有产品时，从正常入口取画面。主动查同类网站，按[动效选型流程](motion.md#开发时默认走这几步)给代表性区域标出触发、运动、停止和手机状态，再按[高保真审图](ui-design-practice.md#高保真审图)核对主体、排版和边框。
2. 由用户确认这份 UI 图。评审稿复用有效素材，缺图标时可用明确标签标位置。用户同意后再制作缺少的图标和图像。
3. 核对控件、素材与设备约束后，决定建法并开始编码。把选定效果接到真实点击、滚动或业务状态，打开页面用[动效验收](motion.md#在成品中验收)核对。最终页面的图标使用已有图形或核定素材。暂停动效、音效开关和 Emoji 按技能入口的页面约定处理。

## 新页面在编码前定四件事

把同一份真实标题、数据和主要操作放入两种明显不同的方向，不靠换一个渐变色充数。每种方向写清以下四项。

| 要定什么 | 要回答的问题 | 常见结果 |
| --- | --- | --- |
| 页面气质 | 访客打开后该感到可信、活泼、克制还是专业？为什么符合这项业务？ | 校园活动可有鲜明节奏，财务和审核后台以稳定、克制为主。 |
| 信息密度 | 用户是快速比较多项，还是理解一个重要主张？ | 列表和后台紧凑排列，官网首屏留出标题、说明和主要动作。 |
| 构图 | 第一眼必须看见什么，图、标题、数据和按钮怎样让路？ | 有明确任务时让数据和操作先出现，品牌图片放在不干扰文字的位置。 |
| 动效 | 动效是否解释状态或层级，能否打断，减少动效时是否仍可用？ | 提交、展开和反馈可有短动效，关键操作不靠循环动效提示。 |

让项目方选方向时，问“哪一版更方便你描述的用户完成任务”，不问笼统的“喜欢哪张”。若没有品牌、真实图片或可商用素材，先用排版、色块和可替换媒体占位确认结构，不能把占位物当成正式视觉资源。

## 从“更大胆、更安静、更紧凑”选一个具体改法

把构图变化、动效强度、信息密度分开。直接采用用户已说清的偏好，缺少方向时才用同一组真实文案和数据试排。选出一个更适合当前人的方案，说明舍弃另一种的代价。[taste-skill 三个维度的作者版本](https://github.com/Leonxlnx/taste-skill/blob/f6831c5df8ad546c2567535442f1691a823868e3/skills/taste-skill-v1/SKILL.md)

| 听到的话 | 改哪一处 | 怎样决定用哪版 |
| --- | --- | --- |
| “活动页想让人记住” | 以活动自己的海报或作品做主视觉，试一版大图不对称构图和一版紧凑日程。两版保留相同的时间、地点与报名入口。 | 面向第一次了解活动的人，优先能辨认活动并找到报名的一版；面向已购票的人，优先一眼找到入场信息的一版。 |
| “官网现在太晃，其他都满意” | 只调动效这一项。保留标题、图片、间距与链接，先减掉装饰层随指针的大范围位移，再看是否还需要降低背景速度。 | 在相同视口重放短划、滚动和静止状态，检查正文稳定、主要按钮能点、减少动画偏好生效。 |
| “审核台多放些信息” | 在现有表格内对齐商户名、校区、状态和操作，隐藏低频详情。动作反馈短而稳定，给行间触控留空间。 | 用同一批含长名称和空字段的申请查一条、审一条、返回继续。这一步仍需寻找时再调密度。 |

新网页选一种与题材相关的识别元素，例如以作品的裁切比例贯穿首页和案例页。旧站只在需要改变相应范围时用这套方法。[Hallmark 项目](https://github.com/Nutlope/hallmark)

## 对已有页面改版前的功能基线

改视觉前，建立一张只覆盖本次受影响范围的功能清单。它既是设计约束，也是改后验收单。

| 类型 | 逐项记录什么 | 改后怎么验证 |
| --- | --- | --- |
| 内容 | 页面标题、说明、关键数据、空状态和错误文案 | 同一角色、同一固定数据下仍能读到且语义没有变化。 |
| 到达路径 | 入口链接、返回、深链接、标签页和锚点 | 从原入口和直接 URL 各走一次。 |
| 可办的事 | 表单字段、校验、复制、保存、筛选、下载、提交与撤销 | 实际点到结果，失败时还能看懂怎样继续。 |
| 身份与范围 | 登录状态、角色按钮、数据范围与审核权限 | 用获准的隔离账号或夹具，确认受限角色没有获得额外操作。 |
| 可见反馈 | 加载、成功、失败、无权和空数据状态 | 将每种状态固定下来，逐个核查内容和下一步。 |

改版只应改变已经说明的视觉系统、布局或交互层级。若用户希望同时删除功能、换业务规则或更改权限，把它单列为产品变更，写清由谁确认，不能混在“美化页面”里。

## 评审与取舍

每次评审按这个顺序输出，避免一句“更高级”掩盖真正问题。

1. 说明两三处应保留的设计和它们服务的任务。
2. 排出最多五个最影响用户的缺陷。每项写“问题、用户影响、具体改法、怎样验”。
3. 把结论分成必须改、建议改和可选探索。核心任务无法办、内容读不清、权限被误导属于必须改。
4. 每轮只改能解释的一两个关系。保留前后同条件截图和一次真实任务记录。

例如“附近门店”列表不能只评图片是否漂亮。先问用户如何选择，才决定一行显示营业状态、人均价、距离、预约或收藏。标题右侧需要操作时，距离可放右下配定位图标，收藏放右上。标签只表达会改变选择的事实，避免重复门店类别。

只有截图时，可直接指出“哪处值得保留、哪位用户在哪一步会迟疑、我会先改什么”，把交互推断标为待操作。拿到可运行页面后，用同角色、同数据、同视口复走，例如有三个实心按钮的预约页，把“确认预约”突出、“改时间”留在日期旁，再用键盘与触屏走一遍改期和确认。交付前后图和操作结果，说明是否仍有重复点击或误解。[Impeccable 作者的评审方法](https://github.com/pbakaus/impeccable/blob/main/skill/reference/critique.md)

## 前后对比交付

同一浏览器、视口、字体、测试数据和登录身份下，保留基线图、改后图和需要时的像素差异图。截图只说明画面是否意外变化，不能替代功能对账。报告至少写：

- 改了什么视觉判断，以及为什么适合这类用户任务
- 哪些功能和数据状态按基线回走过
- 哪些差异是有意改动，哪些仍需人工决定
- 已验环境和未覆盖的设备、账号或生产数据

网页后台还要保留受限角色的对比。管理员可见的操作，不能因为改版在普通员工页面出现。小程序配套项目把这份结论交回小程序流程，继续用真机检查微信端的页面、分享、输入与安全区。
