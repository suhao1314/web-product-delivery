# 网站从讨论到交付

本页是网站开发顺序的依据。新建、改版、加功能、改一行文案、修后端行为和局部修复都从询问需求开始。任何实际开发按下列四步走。其他章节里的做法只能在当前步骤使用。

## 一句话启动网站任务

> 用 $web-product-delivery 帮我做网站。先向我提问并确认需求，再交电脑端和手机端各一张 PNG/JPG UI 设计图。两张图我确认后再出开发方案。我确认这份方案后，才开始做。

用户一句话就能启动询问。新任务先复用已有资料，把仍需决定的部分问清楚。信息齐全时，复述理解，问用户本次目标、范围是否准确，并等他答复。同一任务接着做时只复用实际已按顺序发生、且仍适用于本次范围的确认。

## 网站开发四步

| 当前阶段 | AI 给用户什么 | 推进所需的用户答复 |
| --- | --- | --- |
| 1. 询问并确认需求 | 主动分轮问清使用者、要解决的问题、页面和交付范围、原来怎么做、实际约束和验收结果。先读用户已给的材料以便把问题问准。必要时只读核对当前入口和证据。信息齐了就用白话复述这轮需求。 | 用户明确认可本轮需求。此后开始制作 UI 图片。 |
| 2. 交电脑端和手机端图片并等确认 | 给实际生成或导出的电脑端、手机端 PNG/JPG 图片各至少一张，按范围覆盖受影响页面和状态。新建页面用真实内容做设计图。已有站的文案、修复或不可见的行为变更可在两端画面上标注涉及的入口、预期状态和本次设计。 | 用户看过并明确认可当前这两套图片。图稿有改动就交更新后的图片再核对。 |
| 3. 出开发方案并等确认 | 依据确认后的图说明改哪些页面、行为、组件和数据，怎样验收，涉及哪些成本、兼容性、发布范围或回退。小修可以用几句话讲清。计划还没通过时可继续读资料或解释取舍。 | 用户在看到具体方案后明确同意执行当前方案。 |
| 4. 开发并验证 | 按获准方案制作正式素材和代码，接通功能。从原入口与同一组数据复验桌面、手机、成功、失败和返回等受影响路径。按实际授权处理试用或发布。 | 交可用入口和真实验证结果。发布有对应授权时从目标地址核对版本及恢复办法。[首次发布](first-launch.md) |

第一轮的“你决定”“直接做”“我全交给你”可用于记录偏好。每个阶段仍要出示该阶段的产物，等用户的相应确认。资料齐全且范围确定时，需求确认可以很短。未确认的阶段保持暂停。

## 电脑端与手机端图片怎么交

- 输出两份独立的图片文件，优先小写 `png`，也可用小写 `jpg`。例如 `ui-desktop-r1.png` 和 `ui-mobile-r1.png`。按项目设备选择画布，缺省可以先用桌面 1280 和手机 390 像素宽。图片中给足文字、关键区域和状态，交前实际打开看清楚。
- 在用户能直接看到的回复里分别展示图片，或附可直接查看和下载的实际图片文件。可以使用设计工具绘制并导出。网页链接、可点击 HTML 原型、文字线框、代码或单独一张截图仅能做材料，不能代替成对的 UI 设计图。在图片能力暂不可用时停在出图阶段。
- 已有站的一个小改可以用原画面标注来画目标状态。比如在两端的审核界面标出返回时要保留的筛选，并配图说明预期焦点。标注稿属于设计预期，实际效果在方案获准开发后核对。第一屏、色彩、文案、动效和站点标识按适用范围加入图片。[选版式](layout-patterns.md) · [高保真审图](ui-design-practice.md#高保真审图) · [网站图标和标题](site-identity.md)

## 每次开工前核对三处确认

第一次修改网站文件、创建项目骨架、装依赖、接接口或做项目配置前，按最近的用户答复核对以下三项。记录在当前对话或已有项目记录即可。

1. 哪一条用户回复确认了本次需求和范围。
2. 电脑端和手机端图片各是哪一版，哪些用户回复明确认可了当前使用的两套图片。
3. 当前开发方案在哪里，用户看过它以后哪一条回复同意执行。

缺一项就停在对应步骤。用户回复“收到”“我先看看”或给修改意见时，当前阶段继续等待或修订。用户看到当前产物后明确说“这两张图通过”或“按这份方案做”，按他确认的具体对象继续。新增目标、换图或改方案时，回到受影响的步骤，等新的确认再继续。沿用已确认的内容时，给用户指出这次实际在用的版本。

### 跨对话怎么接着做

用当前对话或项目已有的进度记录记下这些信息。任务很短时，可以简写在一条消息里。

```text
本次目标和范围版本 | 用户确认所在的回复
桌面 PNG/JPG 文件或版本 | 展示位置 | 用户确认所在的回复
手机 PNG/JPG 文件或版本 | 展示位置 | 用户确认所在的回复
开发方案版本 | 展示位置 | 用户看过后同意执行的回复
当前阶段 | 下一步要交的内容或要等的确认
```

恢复时核对记录与用户原话。一次回复可以确认当时已展示的两套图。 需求范围改变时，先确认新范围，再检查已有图片和方案是否仍覆盖这轮任务。只记了“已确认”而找不到对应的用户答复时，回到最早缺确认的步骤补齐。比如只换手机图，可以沿用适用的桌面稿，展示当前这一对图片让用户认可，再按这两套图交开发方案。此前根据旧图同意的方案要重新核对和确认。只调整实施方式时，沿用仍适用的需求和图稿，请用户确认修订后的方案。

## 分轮向用户了解真实情况

一轮先提 1–3 个关键问题，继续问到确实能描述这次要做什么。已说过的信息可以归纳成一句待确认的理解。用户尚无答案时，讲清常见选项和你推荐的理由，等他选。可用结构化提问工具时使用实际可用的工具，否则在对话里直接问。

| 阶段 | 把哪些问题问清 |
| --- | --- |
| 需求 | 谁在哪种设备上用？想办成什么？要新建还是改动哪一处？哪些页面、流程和条件是本轮范围？怎样判断这次有效？ |
| UI 审图 | 当前两张图片上的主体、主操作和结果是不是用户想看到的？有什么地方要改？ |
| 开发方案 | 入口、数据去向、实施步骤、验证条件和可能影响是否正确？用户是否同意按当前方案开始？ |

只请评审、咨询或讲解时，先向用户确认他要看的具体场景，交付所委托的内容。若他随后委托改动，就从本次改动的需求确认进入四步。离线练习只使用自身的示例；用到真实项目时仍按以上顺序。

## 优化或重做已有网站

1. 先核清用户体验到的问题、想改的边界和验收结果。用被授权的入口和同一角色查当前行为。只有截图时按可见区域检查，把运行中的表现留到有实际环境再验证。[按任务复走](journey.md)
2. 需求确定后给电脑端、手机端 PNG/JPG 图。小改可以用现有组件与画面描绘受影响的那一处。整体改版也记录原入口、字段、链接、状态、业务规则和权限。[改版基线](visual-direction-and-change-control.md#对已有页面改版前的功能基线)
3. 用户确认两套图片后交改法与验收方案，等明确同意后才改。完工时用同角色、入口、数据和视口对照原路径和受影响的异常或返回路径。延迟、写入和权限用获准环境验证。
