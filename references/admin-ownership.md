# 首位超管、最后一位超管与人工处理

从零交付后台时，问业务方“正式交付后，遇到所有人都处理不了的工单，谁有权拍板？”把答案落实到产品内可登录的个人账号。接手现有系统时，从工单详情追到服务端的角色、对象范围和状态判断。沿途找出第一次把“待核实”变成“谁也点不了”的地方。

## 谁开通，谁接手

| 时点 | 责任人与交付动作 | 怎么验 |
| --- | --- | --- |
| 首次开通 | 业务所有者指定首位具名负责人。交付工程师提供受控的一次性开通流程，绑定已核实身份；负责人用自己的登录方式接管。普通访客注册不会获得超管权限。 | 空实例并发执行两次开通，只有指定身份获得首管。负责人重新登录能管理账号、范围及业务例外，再走一次开通不会多出超管。用过的临时访问随交接结束。 |
| 正常值班 | 最高超管拥有其负责的产品实例内全部产品管理权限，覆盖各校区、模块和人工处置入口。普通运营、校区管理员与技术运维按职责授权。接单开发者后续需要协助时由负责人单独授权。 | 为新增模块列出菜单、详情、动作、对应服务端权限。分别用唯一超管和受限运营走一次，两端对同一角色的判断一致。多客户部署再核对客户边界。 |
| 交接与恢复 | 先让继任者接受授权、独立登录并核实能管理账号，再允许原负责人退出。仅剩一位时，“交接超管”应直接可用。账户丢失走事先约定的归属核验与恢复流程，记录恢复并撤销临时权限。 | 在两个并发交接或停用请求之后，仍至少有一位可用超管。恢复演练在隔离环境做。小团队可由一人值班，有第二位负责人时可安排备用。 |

这里的职权针对产品自身。支付渠道、身份提供方或客户独立实例各有自己的授权主体。设计界面时写出当前负责人能采取的实际动作。有关首管临时身份和所有者连续性的不同做法，可参照 [Keycloak 管理员交接](https://www.keycloak.org/server/bootstrap-admin-recovery) 和 [GitHub 组织所有者建议](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/best-practices-for-organizations)。

## 把“未核实”拆到具体动作

| 现场情况 | 唯一超管看见什么、能做什么 | 提交后什么算成功 |
| --- | --- | --- |
| 商户缺可选门头照，系统没法自动通过，现有材料允许人工判断 | 同屏显示缺哪项、现有依据和“人工审核”。可选“通过认证”“退回补材料”或“驳回”。高影响决定按业务需要确认一次。 | 服务端回读该申请的新状态、经办人与时间。关闭详情后仍在原校区队列，能接着审下一条。 |
| 协商超过处理期限、当前阶段在等对方，平台有权介入 | 普通运营看到当前责任方。超管还看到“平台介入”，能看原记录、写决定并通知当事人；界面先说明决定对谁生效。 | 同一工单留有处理依据与结果。刷新、重复点击只产生一次决定及关联副作用。 |
| 退款渠道超时，是否已受理未知 | 显示原单、最后查询时间和“查原单回执”“登记核账进度”。负责人可以马上接手。结果未知期间保留待核验和原单占额。 | 回执与原交易匹配后更新执行结果。网络重试没有第二笔退款。仅登记备注不能变成“已到账”。 |
| 明确制度要求独立复核，或对象确实属于另一客户 | 指明该项要求的来源、所缺资格和可联系的责任方。若制度要求双人而当前只有一人，能发起配备复核人的流程并保留工单。 | 授权责任人接到可处理的事项。只有项目确有此要求才设计这条分支。 |

每次遇到禁用按钮，问“什么事实还缺？谁能补？现在点哪里？”把原因和最近一步放在同一屏。人工决定通过正常业务接口提交，服务端核对身份、范围与记录版本，记录对象、操作者、决定、必要理由与前后状态。普通备注、查看材料等低风险动作直接完成。用手机看一次长原因，确认操作键始终可达。

**验收时只留一名有效超管。** 从正常菜单进入同一条有疑点的申请，分别走继续处理、取消、刷新回读。核对取消时零写入，处理时一次生效。换校区运营核对其可操作范围，再模拟外部回执延迟。把“是否有处置权”“能否启动处理”“是否已经执行成功”分别记下。纯 UI 模拟只能验证看见和点到的部分。
