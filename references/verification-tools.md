# 按风险选验收工具

工具只为一个明确问题服务。先写下用户路线、可观察结果和测试数据，再选择最小的一组。公开官网与登录后台分开验收。商家认证、校区切换和权限等后台操作只用脱敏夹具或获准的测试环境，不能把生产地址当负载实验目标。

| 触发情形 | 首选工具与做法 | 留下的证据 | 低成本做法 |
| --- | --- | --- | --- |
| 同一按钮、抽屉或审核卡在不同状态下容易变形 | [Storybook](https://storybook.js.org/docs/writing-stories) 用固定数据单独呈现组件，挑实际存在的状态，如加载、长文本或权限受限 | 每个相关状态的可打开预览和审阅结论 | 在项目演示页用固定 JSON 切换状态 |
| 需要让页面在慢请求、成功、失败、权限拒绝下都可复现 | [MSW](https://mswjs.io/docs/) 在浏览器或 Node 拦截请求。开发、Storybook 和端到端测试共用同一组业务夹具 | handler、夹具、浏览器任务结果 | 本地 API stub，明确它只覆盖这一条路线 |
| 后端接口的状态码、字段和处理顺序有约定 | [Hurl](https://hurl.dev/docs/) 用文本请求和断言走测试环境，覆盖“当前操作者可看”和“无权者被拒” | 可重复运行的 `.hurl`、响应断言和测试环境说明 | 用项目已有 API 测试写同一份断言 |
| 内容更新后担心咨询、产品、课程链接失效 | [Linkinator](https://github.com/JustinBeckwith/linkinator) 爬本地构建产物或获准的预发布站。区分外链临时超时和内部坏链接 | 扫描 URL、状态、排除规则、复核结论 | 从首页和深链接手动点完本轮新增入口 |
| 页面改了却看不出边距、按钮或小屏布局回退 | [Pixelmatch](https://github.com/mapbox/pixelmatch) 对同一浏览器、视口、DPR、字体和测试数据的截图做像素差异。差异图只用来定位，再由人确认是否符合设计意图 | 基准图、当前图、差异图、阈值和人工结论 | 保留同尺寸前后截图并逐项审看 |
| 手机操作、键盘、名称或对比度容易被遗漏 | [axe-core](https://github.com/dequelabs/axe-core) 扫关键页面和弹窗状态，再手动走焦点、错误提示、关闭返焦及手机键盘遮挡 | 规则结果、人工路线、仍需真机验证项 | 按可见名称点击并用键盘 Tab 走一遍主流程 |
| 重构后有未使用文件、导出或依赖，构建和首屏负担变大 | [Knip](https://knip.dev/) 在单独变更中先报告，再逐项确认动态导入、框架约定和生成文件。不要依据首次扫描直接删除 | 配置、报告、每个保留或移除理由 | 审看本轮新增 import 与构建输出 |
| 筛选、分页、权限范围、草稿恢复在边界组合下容易出错 | [fast-check](https://fast-check.dev/docs/introduction/getting-started/) 为不变量生成输入。例如切换校区后绝不能保留旧校区对象 ID，取消拒绝不得产生写入 | 不变量、种子、失败样本及修复后的复跑 | 写出几个最小边界用例，例如第 20/21 条、空队列和跨校区返回 |
| 每次提交都想防止移动端性能、可访问性或 SEO 回退 | [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) 测本地构建或预发布 URL。只把长期稳定、与项目目标有关的指标设为门槛，版本升级后重建基线 | 配置、同条件报告、门槛理由 | 用本技能的 `measure-page.cjs` 记录同条件冷启动样本 |
| 接口单次响应正常，团队需要估计容量 | [Grafana k6](https://grafana.com/docs/k6/latest/) 在自有隔离环境用虚构数据和有上限的少量并发验证具体假设，观察错误率与响应时间分位数。手机首屏另测浏览器绘制与交互 | 环境、样本时长、并发上限、阈值与停止条件 | 先记录单用户请求耗时，确认慢在接口还是页面 |

## 一条路线怎样组合

**截图相同，下拉框却找不到。** 打开[教学样站的咨询页](../assets/site-starter/inquiry.html)，找到“你想聊的方向”。在浏览器开发工具中临时移除这段文字所在 `label` 的 `for` 属性，保留可见文字和样式，再截同尺寸图、跑 axe-core 的 `select-name` 规则。刷新恢复，按控件名称选“产品展示页”，生成摘要并检查结果。用户反馈来自读屏软件时，还需在对应设备听实际播报。

本例在本机 Chromium 的 390×844、1280×844 视口实测。两个视口中，单改标签关联时 Pixelmatch 都报 0 像素差异，axe-core 都定位到 `#topic`；单改下拉框背景色时，Pixelmatch 都检出变化。两次刷新恢复后均能生成摘要。这个对照只覆盖一项名称规则和一项可见变化。

以“手机审核下一条商家申请”为例，用项目现有测试数据准备第 20 和第 21 条申请，从第一页末条打开详情、切到下一条、关闭详情。记录焦点回到哪条、页面有没有再次从头加载。如果迟到的响应会让问题时有时无，再用项目已有模拟接口或 MSW 固定响应顺序。要核实服务端数据范围时，单独运行现有授权用例。每个结果注明使用的账号、环境与数据。

两页官网直接在浏览器从首页点到目标页，记录一次真实交互。页面多到人工容易漏链接时再选 Linkinator；有反复的性能回退和人维护基线时再选 Lighthouse CI。连续动效用录屏或连续帧验证，另试减少动效和触屏滚动。

## 何时停止加工具

一个首版官网通常从浏览器任务走查、同条件性能样本和链接检查开始就够了。后台处理真实资金、身份、权限或多校数据时，再加模拟接口、授权接口断言和不变量测试。Storybook、视觉回归、持续性能门槛和负载实验需要团队能维护基准、夹具与报告，否则会制造无人处理的红灯。

每次报告写清环境、角色、入口、数据来源、实际结果和未覆盖项。工具产生的通过结果只说明它覆盖的规则或夹具，不能代替用户任务、真机或线上回读。

## 外观改版还要做功能对账

整体视觉更新先按[视觉方向与改版护栏](visual-direction-and-change-control.md)保留入口、字段、校验、权限和状态的基线。Pixelmatch 能发现画面差异，却不知道“保存草稿”按钮是否仍可用、普通员工是否多出了审核权限。截图比较之后，用相同账号、数据和入口回走每个受影响动作，再将差异写为预期改动或待修问题。
