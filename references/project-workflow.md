# 网站从讨论到交付

## 从零建站的四步

| 当前步骤 | 做什么 | 什么时候能继续 |
| --- | --- | --- |
| 1. 讨论业务和首版范围 | 看已有材料，分轮向用户提问。复述谁会来、要办什么；给首版范围的建议、要用的内容、费用或维护上的选择，以及一个能实际验证的结果。 | 用户确认需求与首版范围，或已给过这份确定的范围。 |
| 2. 先出 UI 设计稿 | 用真实内容把主路径和代表性页面画出来。交一份能打开的桌面与手机稿，覆盖范围内的页面及关键状态，共用版式可共用设计。标出图标、标签页标题、资源缺口、交互和触屏反馈。方向确有分歧时用同一组内容试两种排法，说明你选哪一版。 | 用户看到并确认具体 UI。根据意见改稿，再核对变更处。确认后补缺的素材。[版式与审美评审](ui-design-practice.md) · [网站图标和标题](site-identity.md) |
| 3. 再出开发方案 | 以确认稿为依据。说明页面和入口怎么接，选哪套现有工程、组件或静态文件，表单交给谁，是否需要登录、保存、管理端和付费服务。列出会先做哪条路径、怎么验、谁发布与维护。把会改变成本或使用方法的选择问清楚。 | 用户确认这份方案，或已明确委托该范围内的技术选型并认可相关业务、费用与数据决定。 |
| 4. 开发、验收和交接 | 沿已定方案做一条可操作路径，再补同一范围内的页面和状态。按同一入口查成功、失败、重试、返回和相关角色。用桌面与手机宽度打开，交实际可用的入口和证据。 | 约定的结果可复验。发布有对应授权时，从目标地址核对版本及恢复办法。[首次发布](first-launch.md) |

只有一句“帮我做网站”，从讨论开始。需求与范围未定时可以查材料、问问题和给首选。等用户确认范围再出图。UI 确认前做的是评审稿，开发方案确认前只推进不依赖它的工作。用户已经交付并确认的范围、图稿或方案可以直接沿用，核对剩余条件后从缺的一步继续。

比如做摄影作品站，先问访客是谁、看完怎样联系。听到“微信接单”时，先问要访客自行联系，还是网站要接收、保存并分配需求。需要从浏览器直接打开微信时，核对目标设备与平台能力，再把实际可行的入口写入稿。选定访客自行联系时，首版可用作品页加咨询页。稿里要看到访客选择作品、写一句需求、回去修改时分别是什么样子。评审通过后再决定生成可复制摘要的静态方案，交付时用虚构需求从作品一路点到结果。若项目方必须收到并分配工单，确认数据和维护责任后才接共享后台。[跟做首站](build-your-first-site.md)

## 分轮向用户了解真实情况

每次问 1–3 个会改变本轮决策的问题，先读对话、项目文件、现有站和标注稿里的答案。用生活化选择和一个有理由的首选帮助用户判断。已答过的直接采用。用户说“不知道”时，解释两种选择会怎么用、要谁维护，再请他选。可用结构化问题工具时优先用实际可用的工具，也可以在对话内编号提问。

| 什么时候问 | 哪些问题值得问 |
| --- | --- |
| 刚开始 | 谁用这个站、在什么设备用，办成什么才算有效？现有哪些站、素材、真实内容和联系渠道？用户希望跟着动手还是由 AI 代做？ |
| 定首版 | 挑一条动作追问。来访者只想找到联系方式，还是要当场提交、让负责人后台查看？愿意今天做成哪一步？有实际预算或上线时间约束吗？ |
| 审图 | 给用户看同一个真实内容。问他第一眼认出的对象和最想点的入口，再问想参考哪项版式或素材。若已有明确方向，把问题留给影响使用的差异。 |
| 开发前 | 对照已经确认的稿问未定的业务规则。谁能看到表单或审核记录？保存在哪里、谁负责维护？提交失败时访客怎样接着办？功能、费用和数据都已明确时，直接给简明方案。 |

带做时先从现场认出用户所在项目、现有工具与会操作的步骤。每轮交代当前走到哪、这一步要产出什么、点哪里能确认成功。用户选择自己操作时，给对应操作和成功标志。用户把获准的操作交给 AI 时，直接做并读回结果。普通环节只保留必要提示。较长项目沿用已有进度记录，写当前版本、已确认范围、样张位置、未决事项和下一步。下一次先按记录和实件恢复，原样沿用有效确认。

## 优化或重做已有网站

1. **找到真实起点。** 确认当前维护的源码、使用入口、版本和操作者。在代表性视口用同一对象从正常入口做到结果。查布局、操作反馈和返回，也查有证据的错误、资源等待及权限边界。手上只有截图时，按可见区域评审并标明待操作核对的项。[按任务复走](journey.md)
2. **把感受说成具体问题。** 先找阻断操作、数据丢失或对象串位，再看阅读和识别障碍。逐项写「在哪一步 → 对谁造成什么影响 → 我建议怎么改 → 如何证明有效」。例如“首屏看起来很乱”可以用访客能否说出服务、找到咨询来判定。把有作用的设计、已习惯的动作和正常入口留在评审里。
3. **按变化量选择投入。** 单纯要建议就交排序与可落地改法。已经委托修复一个明确问题时，用现有工具复现，沿用样式、组件及原入口做可回退的小改，按同条件复验。需要改变数据保留、收费服务或上线范围时，先核对对应决定和授权。涉及全站、主导航或主要版式的重构时，先写清受影响的页面、链接、字段、状态、权限和本轮保留项，让用户确认改版范围。接着走 UI 稿与开发方案两步，从获准的测试副本动手。[改版基线](visual-direction-and-change-control.md#对已有页面改版前的功能基线)
4. **用老路验证新结果。** 同角色、入口、数据和视口对照改前改后。改版至少走一条原有主路径和一条被影响的异常或返回路径。修速度以同条件指标和实际操作比较。角色或数据范围有变化时用隔离测试身份核对服务端。只在授权的环境操作，报告静态图、实际浏览器、真机、预览或正式站各自验证到哪一步。

每次只问会影响正在修改的部分。用户已给网址和流程时可先做只读走查，找到证据后再提问。保留已确认的品牌和业务规则，拟从局部优化扩大到重构时写出为什么，以及会影响哪几项。
